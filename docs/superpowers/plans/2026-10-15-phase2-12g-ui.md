# The Web UI of APT, YUM and apk Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Everything the server does for APT, YUM and apk can be done, and seen, in the web UI: the three formats in every list, the repository form's new fields, a repository's signing key, how a machine is set up to use it, the members a group left out, and uploads.

**Architecture:** One backend change: each format says how a machine is set up to use a repository (`Format.setup`), and the browsing API gives it with the repository, as it gives a component's usage. The rest is the frontend's: `repository-form.ts` learns the three formats' settings; the settings screen gets their fields and facts, a signing-key panel of its own (`signing-key.tsx`) and a group's members left out; the upload form gets their fields; the browse screen shows the set-up commands. Texts are in `messages/en.json`.

**Tech Stack:** Python 3.13 and FastAPI; Next.js, React, TanStack Query, next-intl, Radix; Vitest with Testing Library and axe; Playwright against the built images.

**Spec:** [docs/superpowers/specs/2026-10-14-linux-package-formats-design.md](../specs/2026-10-14-linux-package-formats-design.md), section 8 and the row of plan 12g in section 12, with what plans 12a to 12f settled (P to U in section 4): 4.2 for the signing key, 4.5 for members left out, 5.2, 6.2 and 7.2 for how a machine uses a repository.

## Decisions this plan settles

| # | Decision | Reason |
| --- | --- | --- |
| V1 | How a machine is set up is the format's to say (`Format.setup`, nothing unless a format says), and the browsing API gives it with the repository (`GET /api/v1/content/<name>`: `setup`, as `usage` is for a component), with the address the base URL gives. A part a person fills in is written `<so>`; the account is the shell's `$MEGOOARTI_USER` and `$MEGOOARTI_TOKEN`. | Spec 8: whoever may read a repository needs it, and not only an administrator. | V2 | APT's: the key to `/etc/apt/keyrings/<name>.asc` (not for a proxy, whose `signed-by` is the distribution's keyring), the `deb` line with the hosted repository's suite (`<suite>` for a group or a proxy), and the account in `/etc/apt/auth.conf.d/<name>.conf`, whose `machine` is the host for HTTPS and `http://<host>` for plain HTTP. | V3 | The set-up commands are on the repository's browse page; the signing key, a group's members left out, the suite and the depth are on its settings page. | The first is for whoever uses the repository, the others for whoever keeps it. |
| V4 | The suite and the depth are fields only while a repository is made, checked there as the server checks them; afterwards they are facts, and are sent back unchanged with every save. ## Global Constraints

- **What the UI says is in `messages/en.json`**, and a text is a message of next-intl (ICU): a `<` would start a tag, so none is written; `{name}` is a value.
- **Every screen meets WCAG 2.1 AA** (axe, in the unit tests and in both modes in the browser), and is used by keyboard alone. A field says its hint, or what is wrong with it, through `aria-describedby`.
- **A secret is kept nowhere it was not asked to be**: a private key that was sent is in neither the page's state nor TanStack Query's cache once the server has it (`gcTime: 0`, `reset()`), as a proxy's password is not.
- **The UI fetches nothing from another host** and runs under its content security policy; a `data:` link is a download, not a request.
- **A table's line under its headings is `| --- | --- |`.** Commits end with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

**Working directories:** run `uv` and `pytest` commands in `backend/`, `pnpm` commands in `frontend/`, and `git` commands in the repository root. Backend tests need the `db` Compose service; set `MEGOOARTI_TEST_DATABASE_URL` as `docs/development.md` describes. After an API change the OpenAPI snapshot is written again with `MEGOOARTI_UPDATE_OPENAPI=1 uv run pytest tests/test_openapi_snapshot.py` and the frontend's types with `pnpm gen:api`.

## Review Focus

What the tests of this plan do not reach, most likely first. The reviewer reads for these.

1. **The address in the set-up commands**: an installation without a base URL behind the gateway, a base URL with a path (`https://example.com/megooarti/`), a host with a port, and the `machine` line of apt's credentials for each; apk's address with the account in it when the user name or the token has a character an address gives a meaning to.
2. **The private key in the page**: what happens to it on a refusal (it stays, to be put right), on leaving the page, and in the browser's own memory of fields (autocomplete, spell checking).
3. **Long text on a narrow screen**: a set-up command of 600 characters, a fingerprint, an RSA public key of 8192 bits, in the panel at 360 pixels: nothing may push the page sideways.
4. **What the page reads of the server's words**: the `Left out of the group <name>: ` prefix, and a reason cut at the 255 characters a last error keeps.
5. **A key replaced elsewhere** while the page is open (another administrator, the API): the panel shows the key it had until it is asked again, and the download is of that one.

## 1. Purpose

Make MegooArti a Maven repository manager: somewhere to deploy a team's own artifacts, a cache in front of Maven Central, and one URL that presents both.

Success means:

- `mvn deploy` publishes a release and a snapshot to hosted repositories with no client-side workaround.
- `mvn` builds a project whose dependencies and plugins all arrive through a group made of those hosted repositories and a proxy of Maven Central.
- `maven-metadata.xml` and checksum files are always consistent with the files the repository holds, including after a delete and after two deploys at the same moment.
- The npm, PyPI and Docker plans can reuse the core changes made here without reopening them.

## 2. Scope

| **4b** | Core changes for proxy and group formats (section 4.2); Maven proxy; metadata merging; Maven group; a real `mvn` build through a group |

## 3. Decisions

| # | Decision | Reason |
| --- | --- | --- |
| D1 | Checksum files are never stored. A request for one is answered from the hashes recorded for the file it belongs to. An uploaded checksum is compared with that file, then dropped. | A stored checksum can disagree with its file; a computed one cannot. Every blob already has all four hashes. |
| D2 | On a hosted repository, `maven-metadata.xml` is generated on each request from the files the repository holds. Uploaded metadata is accepted and dropped, except plugin prefixes (D3). | Client-merged metadata loses versions when two deploys overlap and goes stale after a delete. Generated metadata cannot. |
| D3 | Plugin prefixes are taken from uploaded group-level metadata, merged, and stored by the server. | Only the plugin's jar knows its prefix. Everything else in the metadata can be derived from file names. |
| D4 | Version policy is fixed when a repository is created. | Changing it would leave content the repository refuses to serve. |
| D5 | A proxy serves the remote's `maven-metadata.xml` as received. Only a group builds a new document, by merging its members'. | A proxy does not hold every version, so it cannot generate the list. |
| D6 | Each engine (hosted, proxy, group) is a hook on the format, with the generic engine as the default. | Maven needs to answer some paths itself in all three; so will npm, PyPI and Docker. |
| D7 | `latest` and `release` are the highest versions by Maven's version order, not the most recently deployed. | It is deterministic and does not depend on deploy order. Nexus's rebuild does the same. |
| D8 | Maven compatibility is tested by running the Maven CLI in a container against the built image. | The BRD makes real clients the definition of done (NFR-1, R-2). |

## 4. Changes to the core

These amend section 6 of the storage design. Raw's behaviour does not change.

### 4.1 For hosted formats (plan 4a)

- **A component is optional.** `describe_component(path)` may return nothing, and the file is then stored with no component. Maven uses this for files outside the Maven layout in a permissive repository.
- **Format settings can see their previous value.** `validate_config(type, config, current)` receives the stored settings on update, so a format can refuse to change one (D4).
- **Answering with generated bytes.** The context can answer a request from bytes held in memory, through the same code that plans a response for a stored file. The response therefore has the same headers as in section 7.2 of the storage design, the same conditional and range handling, and the same three protective headers.
- **Reading without tables.** Formats still never query tables. The context gains read operations that return plain values:

  | Operation | Returns |
  | --- | --- |
  | Describe a path | Size, the four hashes, content type and modification time of the file there, or nothing |
  | Versions of a package | The versions that exist for a namespace and name |
  | Files of a component | Path and modification time of each file of one namespace, name and version |
  | Read a small file | The bytes of a stored file, refused above a stated limit |

- **Server-maintained metadata.** A new operation, `maintain(path, update)`, changes a document the server keeps on the uploader's behalf. `update` receives the stored bytes, or nothing, and returns what to store, or nothing to remove the document. It runs under the path's lock, so two changes never overwrite each other. The operation needs `add` or `edit`, refuses a read-only repository, is not subject to `disable_redeploy`, records the kind `metadata` with no component, and refuses to touch a file of any other kind. A format therefore cannot use it to overwrite an artifact.
- **Reading a small upload.** `receive(stream, limit)` gives the database connection back and reads a body of at most `limit` bytes into memory, so a format never handles the session to do so.
- **Accepting an upload that stores nothing.** `require_write()` applies the same check as `maintain` without storing. A format calls it before accepting an upload it will drop, so that dropping is never a way around permissions. Both it and `maintain` refuse to run on a repository that is not hosted.

### 4.2 For proxy and group formats (plan 4b)

- **Engine hooks (D6).** The format has `handle_proxy` and `handle_group` beside `handle_hosted`. The dispatcher calls the hook for the repository's type. The base class forwards to the generic proxy and group engines, which do not change behaviour.
- **Fetching is separate from answering.** The proxy engine exposes `ensure_cached(context, path)`: make the path servable from the cache, or raise `404` or `502`. It contains everything section 8 of the storage design describes (freshness, revalidation, negative cache, blocking, one download per path). The engine's request handler becomes: check the method, call `ensure_cached`, respond.
- **The outbound client travels with the context**, built on first use as today, so that code which fetches does not need the request.
- **`ensure_cached` commits.** It commits before waiting for a download and after recording its result, as the proxy engine already does. This is now stated as part of its contract: a caller must not have uncommitted work of its own when it calls it.
- **Visiting a group's members.** The group engine exposes the walk it already does (members in order, offline ones skipped, each group visited once per request) so that a format can ask every member instead of stopping at the first.

## 5. Maven paths

A path is classified before anything else happens.

| Kind | Shape | Example |
| --- | --- | --- |
| Checksum | Any path ending in `.md5`, `.sha1`, `.sha256` or `.sha512`. It belongs to the path without that ending | `…/app-1.0.jar.sha1` |
| Metadata | `maven-metadata.xml` in a directory | `com/acme/app/maven-metadata.xml` |
| Artifact | `<group dirs>/<artifactId>/<version>/<file>` (see below) | `com/acme/app/1.0/app-1.0.jar` |
| Catalog | `archetype-catalog.xml` at the root | |
| Other | Anything else | `notes/readme.txt` |

**Artifact paths.** There is at least one group directory, and no group directory contains a dot, so a path and its coordinates map one to one (`com/acme` is `com.acme`). The file name starts with `<artifactId>-<version>`, followed by an optional `-<classifier>` and then `.<extension>`. The extension is everything after the first dot that follows, so `tar.gz` and `jar.asc` are extensions. Signature files are ordinary files.

**Snapshots.** A version directory ending in `-SNAPSHOT` is a snapshot. Its files are named either with a timestamp and build number (`app-1.0-20261008.101500-3.jar`) or, in the older style, with the literal version (`app-1.0-SNAPSHOT.jar`). Both are accepted. A metadata path directly inside a snapshot version directory is *version-level* metadata; any other metadata path is *artifact-level*.

**Components.** An artifact file belongs to the component whose namespace is the group ID, name is the artifact ID and version is the version directory. Every build of `1.0-SNAPSHOT` belongs to one component. Catalog and other files have no component.

**Content types.** Maven clients rarely declare one, so the format sets it from the extension for the types Maven uses (`pom`, `jar`, `war`, `module`, `asc`, `xml`), and falls back to the generic rule.

### 5.1 Layout policy

| Setting | Effect |
| --- | --- |
| `strict` (default) | Only checksum, metadata, artifact and catalog paths can be added. A `PUT` to any other path is `400 invalid_path`, and a proxy does not ask its remote for one |
| `permissive` | Other paths are stored and served as plain files |

The policy governs what can be added, not what is served: files stored while a repository was permissive stay readable and deletable after it is made strict.

### 5.2 Version policy

| Setting | Accepts |
| --- | --- |
| `release` (default) | Artifacts whose version is not a snapshot; artifact-level metadata |
| `snapshot` | Snapshot artifacts; all metadata |
| `mixed` | Everything |

A `PUT` to a path the policy excludes is `400 version_policy_violation`, whether or not the upload would have been stored. A `GET` or `HEAD` is `404`, and a proxy does not ask its remote. Catalog and other paths are not subject to it.

Under both policies, a checksum path is treated as the path it belongs to.

Both policies are settings of hosted and proxy repositories, given in `format_config`. A group has none. Sending a different `version_policy` on update is `409 immutable` (D4).

### 5.3 Version order

`latest`, `release` and the order of `<versions>` use Maven's own comparison (`ComparableVersion`): numeric and text segments, the qualifier order `alpha`, `beta`, `milestone`, `rc`, `snapshot`, release, `sp`, and trailing zeros ignored. It is implemented here from Maven's published Version Order Specification, and where that leaves a case open it does what Maven 3.9 does: a qualifier that ends the version, or has a digit directly after it, is treated like one after a hyphen. The Docker-marked suite compares it with Maven itself on a list of versions; where they differ, Maven is right.

## 6. Hosted Maven

| Request | Path kind | Result |
| --- | --- | --- |
| `GET`, `HEAD` | Artifact, catalog, other | The stored file, or `404` |
| `GET`, `HEAD` | Metadata | The generated document (6.2), or `404` if there is nothing to list |
| `GET`, `HEAD` | Checksum | The hash as lower-case hex, `text/plain` (6.1), or `404` |
| `PUT` | Artifact, catalog, other | Stored as in hosted Raw, after the layout and version policy checks. `201` or `204` |
| `PUT` | Metadata | Accepted and dropped; plugin prefixes are kept (6.3). `201` |
| `PUT` | Checksum | Verified and dropped (6.1). `201` |
| `DELETE` | Artifact, catalog, other | `204`, or `404` |
| `DELETE` | Metadata, checksum | `405`: there is nothing stored to delete |

A deploying account needs `add` and `read`, because Maven reads a repository's metadata before it uploads. It does not need `edit`: nothing it replaces is a file it published.

The deployment policy applies to every stored file, snapshots included. A snapshot repository that receives old-style snapshot names needs `allow_redeploy`.

### 6.1 Checksums

**Reading.** The hash of the file the path belongs to. For a metadata path it is the hash of the document a `GET` of that path would return at that moment. `Last-Modified` is that of the file or document.

**Uploading.** `require_write()` first. The body is limited to 1 KiB and read the way Maven reads checksum files: the text after an equals sign and a space if present, otherwise the first word.

| The checksum belongs to | Result |
| --- | --- |
| A metadata path | `201`. It cannot be checked: the client's document is not the one served |
| A stored file, and matches | `201` |
| A stored file, and differs or cannot be read as a hash | `400 checksum_mismatch`, logged with the repository, path and user. The file stays |
| Nothing stored | `404`. Maven, Gradle, sbt and Ivy all send a file before its checksums |

Maven only warns when a checksum upload fails; the build still succeeds. A corrupted deploy is therefore visible in the server log, not to the person deploying.

### 6.2 Generated metadata

**Artifact-level**, for `<group>/<artifact>/maven-metadata.xml`:

- `groupId`, `artifactId`.
- `versions`: every version that has at least one file, in Maven order.
- `latest`: the highest version. `release`: the highest that is not a snapshot; omitted if there is none.
- `lastUpdated`: when any file of the artifact last changed.
- `plugins`: the stored plugin entries for this path, if any (6.3).

The same path can be both an artifact and a group (`org/apache/maven/plugins`), which is why one document can carry both a version list and plugins. If there are neither versions nor plugins, the answer is `404`.

**Version-level**, for `<group>/<artifact>/<x>-SNAPSHOT/maven-metadata.xml`:

- `groupId`, `artifactId`, `version`.
- `snapshot`: the timestamp and build number of the highest build among the timestamped files. Omitted if there are only old-style names.
- `snapshotVersions`: one entry for each classifier and extension, with the value and modification time of its highest build. A pair that exists only under an old-style name is listed with the literal version.
- `lastUpdated`: when any file of the version last changed.

A client deploying the next snapshot reads this document to choose its build number, so it gets one more than the highest build stored.

The document is built with a small, fixed number of queries and is not cached. Its `ETag` is the hash of its bytes, so conditional requests are exact. `Last-Modified` is `lastUpdated`; after a delete it can move backwards, which the `ETag` makes harmless.

### 6.3 Uploaded metadata and plugin prefixes

`require_write()` first. The body is limited to 1 MiB; a larger one is `400 invalid_metadata`.

- **Version-level:** dropped without being read further. `201`.
- **Artifact-level:** parsed. If it cannot be parsed, `400 invalid_metadata`. Its `<plugins>` entries (name, prefix, artifact ID) are merged into the entries already stored for that path, the uploaded entry winning for the same artifact ID. Entries whose artifact has no file in that group are dropped. If any remain, the result is stored with `maintain` at the metadata path as a document holding only `<plugins>`; that stored file is the server's record and is never served as it is. Everything else in the upload is ignored. `201`.

When a document is generated, stored plugin entries whose artifact no longer has any file are left out.

### 6.4 XML

Metadata is the only XML that is parsed. The parser refuses any document with a `DOCTYPE`, so entity expansion and external entities cannot occur, and input is bounded by the size limits above and in section 8. A document nested more than 16 levels deep, or holding more than 20,000 elements, is refused as well: sorting versions is the costly part, and this keeps one document to about a quarter of a second.

## 7. Proxy Maven (plan 4b)

`GET` and `HEAD` only. The path is classified and checked against the layout and version policy before anything else, so an excluded path is `404` without a remote request. A file cached before the layout policy was tightened is still served.

| Path kind | Result |
| --- | --- |
| Artifact, catalog, other | The generic proxy behaviour |
| Metadata | The generic proxy behaviour: the remote's document, cached and served as received (D5) |
| Checksum | `ensure_cached` for the path it belongs to, then the hash of the cached file. For both `GET` and `HEAD`. The remote's checksum file is never requested, so a checksum of a checksum (`x.jar.sha1.sha1`) is `404` |

**What is revalidated when.** Metadata, the catalog and old-style snapshot files change at the remote, so they use `metadata_max_age_minutes`. Release files and timestamped snapshot files never change, and use `content_max_age_minutes`.

A request for the checksum of a file that is not yet cached downloads that file. Clients ask for a file before its checksum, so in practice the file is already there.

## 8. Group Maven (plan 4b)

`GET` and `HEAD` only.

| Path kind | Result |
| --- | --- |
| Artifact, catalog, other | The generic group behaviour: the first member that has it |
| Checksum of any of those | The generic group behaviour: the first member that has the file answers its checksum |
| Metadata | Merged from the members (below) |
| Checksum of metadata | The hash of the merged document |

**Collecting.** Every online member is asked, in order, for its document at that path: a hosted member generates it, a proxy member calls `ensure_cached` and reads its cached copy, a group member merges its own members. A member contributes nothing if it has no document, cannot reach its remote, excludes the path by policy, holds a document larger than 4 MiB, or holds one that cannot be parsed; the last two are logged. If no member contributes, `404`.

**Merging artifact-level documents.**

- `versions`: the union, in Maven order. `latest` and `release` are recomputed from it.
- `plugins`: the union by prefix; the earlier member wins.
- `lastUpdated`: the latest.
- `groupId`, `artifactId`: from the first document that has them.

**Merging version-level documents.**

- `snapshot`: from the document with the latest timestamp, then the highest build number.
- `snapshotVersions`: the union by classifier and extension, keeping the entry updated most recently; the earlier member wins a tie.
- `lastUpdated`: the latest.

The merged document is built on each request and is not cached; for a proxy member that is fresh, collecting is one database read. Its `Last-Modified` is the latest among the contributing members. Building and merging run on two worker threads of their own, with the database connection given back first, so a long list of versions queues behind other metadata and not in front of everything else.

## 10. Code structure

Under `backend/src/megooarti/repositories/`:

| File | Responsibility |
| --- | --- |
| `maven/paths.py` | Classify a path; coordinates; snapshot file names; policy checks. Pure functions |
| `maven/versions.py` | Maven version comparison. Pure functions |
| `maven/metadata.py` | The metadata model: parse (safely), build from versions or files, merge, serialise. Pure functions |
| `maven/checksums.py` | Read an uploaded checksum; name the algorithm for a path. Pure functions |
| `maven/format.py` | The `MavenFormat` class: settings, component description, and the three engine hooks. The only Maven file that touches the context |
| `formats.py` | The two new hooks, optional component, `current` settings |
| `content.py` | The read operations, generated-bytes response, `maintain`, `require_write` |
| `proxy.py`, `group.py`, `dispatch.py` | `ensure_cached`; the member walk; dispatch through the format's hooks |

There is no migration: a file without a component, the kind `metadata` and the needed indexes all exist already.

## 11. Testing

- **Pure functions** are tested directly: path classification and its edge cases, version order against the specification's examples, metadata building, parsing (including refused `DOCTYPE` and oversize input) and merging, checksum reading.
- **Each repository type** is tested through the HTTP API with the existing fixtures, including the fake remote: every row of the tables in sections 5 to 8, permissions on dropped uploads, and both policies.
- **Races** that the shared-transaction fixture cannot show (two deploys of different versions at once; a plugin-prefix merge at once) use the real-transaction pattern from the storage tests.
- **Real client (D8)**, in the Docker-marked suite, which needs internet access:
  - *Plan 4a:* the Maven CLI in a container deploys a release and two builds of a snapshot to hosted repositories, taking its own plugins straight from Maven Central. The test checks the stored files, the generated metadata and the second build number, then resolves both artifacts from an empty local repository.
  - *Plan 4b:* the same, with Maven's settings mirroring everything to a group of the two hosted repositories and a proxy of Maven Central, starting from an empty local repository, so every plugin and dependency arrives through MegooArti.

## 12. Risks

| Risk | Response |
| --- | --- |
| A client depends on reading back exactly the metadata it uploaded. | None of Maven, Gradle, sbt or Ivy does. The real-client tests cover Maven; others are covered in plan 11. |
| The version comparison differs from Maven's in some corner. | It is compared with Maven itself in the Docker-marked suite, and a difference affects only `latest`, `release` and list order, never which files are served. |
| Generating metadata for an artifact with thousands of versions on every request is slow. | It is one indexed query and an in-memory sort. A cache keyed by `lastUpdated` can be added without changing behaviour. |
| A corrupted upload goes unnoticed by the person deploying, because Maven only warns when a checksum upload fails. | The server refuses the checksum and logs `checksum_mismatch` with the repository, path and user. Someone with `delete` removes the file. Removing it automatically would let anyone with `add` delete files by sending a wrong checksum. Marking such a file in the browse API is a candidate for plan 8. |
| A checksum request to a proxy can trigger a large download. | Only for a file the client is about to request anyway; the download is then reused. |
| A group merges on every metadata request. | Metadata is small and clients ask for it at most once a day by default. Caching the merged document is a later optimisation. |
